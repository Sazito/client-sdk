## Module role in sales flow

`payments` is the final checkout module before order completion.

- Depends on invoice credentials (`invoices.create` must run first).
- Supports redirect/post gateways and manual step-based flows like card-to-card upload/code verification.
- When payment reaches `show_order`, SDK runs checkout finalization automatically.

## V2 contract notes

- `payments.getMethods` sends the current invoice identifier to `/api/v2/payments/list`.
- Payment creation can return `id: 0`; v2 then resolves the payment by
  `payment_identifier` at `/api/v2/payments/0/process_payment_step`.
- Gateway-return verification uses the real positive payment ID embedded in
  the callback URL; zero is not accepted as a callback payment ID.
- `/api/v2/payments/{id}/process_payment_step` behavior depends on exact `Content-Type`.
- JSON mode uses exact `application/json`. The SDK sends the wire field as `payment_identifier`.
- Use form mode for gateways that post callback/form payloads.
- Action values are preserved exactly and are case-sensitive; the SDK does not rename them.

## Methods

### Get Methods

Use: `payments.getMethods(options?)`.

Returns available payment methods for current invoice credentials.

```ts
const methodsRes = await client.payments.getMethods();
```

### Create

Use: `payments.create(paymentTypeId, options?)`.

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `paymentTypeId` | `number` | Required | Payment method ID (`PaymentMethod.id`). |
| `options` | `RequestOptions` | Optional | Per-request controls. |

Returns: `SazitoResponse<Payment>`.

```ts
const methodsRes = await client.payments.getMethods();
if (methodsRes.data?.length) {
  await client.payments.create(methodsRes.data[0].id);
}
```

### Initialize

Use: `payments.initialize(options?)`.

Initializes current payment and returns next action.

Returns: `SazitoResponse<PaymentAction>`.

When payment verification succeeds (`action === 'show_order'`), the SDK automatically
calls `POST /api/v1/pinch/order` and clears the completed cart, invoice,
shipping-address, payment, and discount credentials from browser storage.

```ts
const actionRes = await client.payments.initialize();

if (actionRes.data?.action === 'REDIRECT') {
  console.log('Redirect to:', actionRes.data.address);
}
```

### Process Step

Use: `payments.processStep(input, options?)`.

Use this for JSON-mode step requests (commonly `cardtocardpayment`) after `create`/`initialize`.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `input.paymentIdentifier` | `string` | Optional | With `input.id`, restores callback payment credentials; otherwise overrides the stored identifier. |
| `input.id` | `number` | Optional | With `input.paymentIdentifier`, selects the callback payment endpoint and persists both values. |
| `input.payload` | `Record<string, any>` | Optional | Gateway-specific JSON payload. |
| `input.tatoken` | `string` | Optional | Gateway/session token. |
| `input.trackingData` | `Record<string, any>` | Optional | Tracking payload. |
| `input.isFailed` | `string` | Optional | Mark payment failed (`"true"`). |
| `input.imageUrl` | `string` | Optional | Uploaded payment proof URL. |
| `input.code` | `string` | Optional | Verification code (e.g., card-to-card). |
| `options` | `RequestOptions` | Optional | Per-request controls. |

```ts
const cardToCardStep = await client.payments.processStep({
  imageUrl: 'https://cdn.example.com/payment-proof.png',
  code: '894512',
});
```

This produces the exact endpoint body:

```json
{
  "payment_identifier": "<current-payment-identifier>",
  "image_url": "https://cdn.example.com/payment-proof.png",
  "code": "894512"
}
```

### Verify

Use: `payments.verify(input?, options?)`.

Verifies a returning gateway payment with Sazito's URL-encoded form contract.
Gateway values are sent as direct fields with their original names and casing.
When both callback credential fields are provided, the SDK restores them before making
the request, so verification also works when no payment credentials remain in
browser storage:

```ts
const result = await client.payments.verify({
  id: 304,
  paymentIdentifier: '6f8a717eb211f0839e522a5358932968',
});
```

If `id` and `paymentIdentifier` are omitted, `verify` uses the payment created
earlier on the same SDK client and performs one JSON status request.

For server adapters that receive GET and POST callback data separately, use
`verifyPaymentCallback`. Body fields are copied first and query fields second,
so query values win when a field appears in both places:

```ts
const result = await client.payments.verifyPaymentCallback({
  paymentId: 304,
  paymentIdentifier: '6f8a717eb211f0839e522a5358932968',
  body: requestBody,
  query: searchParams,
});
```

Use `getPaymentStep()` for one JSON status request. Callback verification and
pending status polling intentionally use different encodings.

### Process Step (Form Mode)

Use: `payments.processStepForm(input, options?)`.

Use this when gateway flow requires non-JSON form payload handling for
`/api/v2/payments/{id}/process_payment_step`.

This callback branch requires the positive payment ID from the gateway-return
URL; the temporary initialization ID `0` is rejected.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `input` | `FormData \| Record<string, string \| number \| boolean \| null \| undefined>` | Required | Form fields sent with non-JSON content type. |
| `options` | `RequestOptions` | Optional | Per-request controls. |

```ts
const stepRes = await client.payments.processStepForm({
  code: '894512',
  imageUrl: 'https://cdn.example.com/payment-proof.png',
});
```

### Poll Until Settled

Use: `payments.pollUntilSettled(options?, intervalMs?)`.

Polls payment state via JSON every 15 seconds by default until
`action !== 'pending'`. It supports `AbortSignal`, `maxAttempts`, an immediate
first request, and a five-minute default polling deadline.

```ts
const finalAction = await client.payments.pollUntilSettled({
  intervalMs: 5000,
  pollingTimeoutMs: 120000,
  signal: controller.signal,
});
```

### Clear Payment

Use: `payments.clearPayment()`.

Clears persisted payment credentials.

```ts
client.payments.clearPayment();
```

## Response key fields

### Payment Method

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | `number` | Required | Payment method ID. |
| `code` | `PaymentGateway` | Required | Gateway code enum (from `reference_code`). |
| `title` | `string` | Required | Display title (English). |
| `titleFa` | `string` | Required | Display title (Persian). |
| `description` | `string \| null` | Required | Method description; often `null`. |
| `paymentSubType` | `number \| null` | Required | Payment sub-type id; `null` when absent. |
| `order` | `number` | Required | Display order. |
| `isDefault` | `boolean` | Required | Default method flag. |

### Payment Action

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `action` | `'POST' \| 'REDIRECT' \| 'UPLOAD' \| 'show_otp_modal' \| 'show_order' \| 'pending' \| 'payment_fail_error' \| 'show_error' \| 'FAIL' \| 'StockViolated'` | Required | Exact, case-sensitive next action type returned by the API. |
| `address` | `string` | Optional | Redirect/post URL. |
| `payload` | `Record<string, string \| number>` | Optional | Hidden form fields for `POST`. |
| `order` | `CheckoutOrder` | Optional | Required by both `show_order` and `pending`. Response keys inside the order are camel-cased once by the SDK. |
| `time` | `number` | Optional | Upload or OTP window in minutes. |
| `message` | `string` | Optional | Error/action message. |
| `raw` | `JsonObject` | Optional | Complete unnormalized backend result for forward compatibility. |

For `pending`, call `pollUntilSettled()` (15 seconds by default). Polling stops
when the action changes to `show_order` or a failure/unknown action, when it is
cancelled, or when its configured limit is reached.

`CheckoutOrder` describes the payment endpoint's final order, independently of
the account `Order` returned by `orders.get()` and `orders.list()`.
Its invoice can omit `netTotal` and `finalTotal` in verification responses.
Items use `variantAttributes`,
`singleItemPrice`, `noOfItems`, `totalItemsPrice`, and nested `productVariant` data.
IDs retain their string or number values. No invoice-item ID or original price
is invented when the payment response does not provide one.

## Known errors

| Type | When it happens |
| --- | --- |
| `validation` | Missing invoice/payment credentials. |
